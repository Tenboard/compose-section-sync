# Section Sync Workflow

## When to use

`:section-sync`의 기능·선택 규칙·스크롤 상태 변경, `:app`의 라이브러리 연동 변경, 공개 API 검토, 회귀 검증에 사용해주세요. 이 하네스를 수정할 때도 마지막 Validation을 적용해주세요. README 오탈자처럼 실행 동작·API 계약과 무관한 수정에는 전체 절차, 위임, Gradle 빌드가 필요하지 않습니다.

기본 구조는 단일 에이전트 Pipeline입니다. 작은 라이브러리에서 순수 규칙과 Compose 상태 전이를 함께 파악하고, 위험한 변경의 리뷰 누락과 검증 과장을 줄이는 것이 설계 근거입니다. 상시 팀, 역할별 스킬, 런타임 어댑터는 요구하지 않습니다.

## Required inputs

다음 입력은 요청과 저장소에서 먼저 확보해주세요. 결과를 바꾸는 정보만 부족할 때 질문하고, 독립적인 조사는 계속해주세요.

- 목적, 허용 변경 범위, 제외 범위, 관찰된 동작과 기대 동작 또는 검토 질문
- 현재 작업 트리·staged diff, 적용되는 `AGENTS.md`, 관련 소스와 호출부
- [README](../../../README.md), [버전 카탈로그](../../../gradle/libs.versions.toml), Wrapper 및 관련 모듈 Gradle 설정
- 재현 조건과 기존 테스트의 실제 검증 내용, 사용 가능한 JDK/SDK·기기·도구 및 권한

## Workflow

각 단계의 출력은 기본적으로 대화에 간결하게 남겨 다음 단계가 소비하도록 해주세요. 재개·감사가 필요할 때만 아래 영구 인계 규칙을 사용해주세요.

| 단계 | 수행 내용 | 이름 있는 출력 |
| --- | --- | --- |
| 1. 조사 | git 상태와 관련 소스·문서·테스트를 읽고 재현 조건, 지원 범위, 기존 사용자 변경을 확인해주세요. 확인된 사실·추론·미확인을 구분해주세요. | 조사 요약 |
| 2. 계획 | 책임 경계, 최소 수정 파일, 기대 동작, 관련 위험 시나리오와 검증 방법을 정해주세요. “반복되는 실패를 줄이는 가장 작은 구성”에 대한 답을 한 문장으로 남겨주세요. | 변경 계획 |
| 3. 수행 | 승인된 범위만 구현하거나 검토해주세요. 버그 수정 범위라면 원인을 드러내는 회귀 테스트를 함께 다루되, 조사·문서만 요청되었다면 코드 문제와 테스트 공백은 기록만 해주세요. | 변경 diff 또는 검토 결과 |
| 4. 리뷰 | 아래 위험 리뷰 조건에 따라 diff와 연결된 호출부를 다시 확인해주세요. 같은 에이전트도 구현과 구분되는 리뷰 단계를 수행할 수 있습니다. | 리뷰 판정 |
| 5. 검증 | [검증 지침](references/validation.md)에서 변경과 관련된 항목만 선택하고 명령·환경·실제 결과·미실행 사유를 남겨주세요. | 검증 기록 |
| 6. 인계 | 최종 diff를 시작 상태와 대조하고, 변경 이유·남은 위험·완료 상태를 정리해주세요. PR이 필요하면 기존 템플릿에 결과를 넣어주세요. | 최종 인계 |

### 계획과 수행의 경계

- 의존 방향은 `샘플 UI → 라이브러리 공개 API → 순수 선택 규칙`이며, Compose 어댑터가 상태·프레임·수명주기 입력을 연결하도록 해주세요. 순수 계산에 `LazyGridState`나 샘플 데이터 접근을 넣지 마세요. 현재 옵션 타입의 `@Immutable`을 이유로 별도 계층 모듈을 만들 필요는 없습니다.
- [README의 지원 범위](../../../README.md#usage-rules-and-limitations)를 확인해주세요. `LazyColumn`, `LazyHorizontalGrid`, reverse layout, 미로딩 Paging 섹션, Compose Multiplatform을 지원한다고 가정하지 마세요. 지원 확대는 별도 요구가 있어야 합니다.
- 공개 API 또는 기본 동작 변경에는 심벌·시그니처·기본값·예외/취소 의미의 전후 차이, 소스·바이너리·행동 호환성, README와 샘플을 포함한 호출부 영향, Kotlin 사용 예시를 검토 결과에 포함해주세요. 바이너리 호환성 도구가 설치되어 있다고 가정하지 마세요.
- README·KDoc·샘플 각각의 수정 필요 여부와 이유를 판단하고 필요한 변경을 계획에 포함해주세요. 베타여도 호환성 영향을 생략하지 마세요. PR 항목의 원본은 [기존 PR 템플릿](../../../.github/pull_request_template.md)이며, 체크리스트를 새 문서에 복제하지 마세요.

### 위험 리뷰

상태 전이, 요청 취소, Compose 수명주기, 공개 API·기본 동작을 바꾸면 명시적인 리뷰가 필요합니다. 요청 교체·성공·취소·폐기·입력 변경·dispose의 전후 상태와 부작용을 따라가고, 선택 유지 및 상위 Job 보존을 검증 시나리오와 연결해주세요. API 변경은 위 호환성 검토도 소비해주세요.

리뷰 판정은 `pass`(진행 가능), `fix`(구체적인 수정 필요), `blocked`(판단에 필요한 정보/능력 없음)로 남기고 근거 파일을 명시해주세요. `pass`는 테스트 성공을 뜻하지 않습니다. 문서 오탈자 등 낮은 위험 변경은 diff 자체 검토로 충분합니다. 수정 후에는 바뀐 부분과 실패한 검증을 다시 확인하고, 같은 원인의 실패를 무제한 반복하지 마세요.

### 선택적 읽기 전용 위임

독립적인 조사나 리뷰의 병렬 처리·문맥 분리가 조율 비용보다 유리할 때만 위임해주세요. 짧은 지시문에 아래 계약을 채우고, 기본 깊이는 `owner → reader` 한 단계로 제한해주세요. 고정 팀이 필요하지 않아 별도 team-spec은 두지 않습니다.

| 계약 | 지정할 내용 |
| --- | --- |
| 책임·입력 | `owner`는 전체 조사·구현·검증·통합을 담당합니다. `reader`는 한정된 조사/리뷰 질문, 읽을 경로, 기준 commit 및 작업 트리 변경 내용을 받습니다. 같은 스킬의 관련 부분만 적용해주세요. |
| 출력·완료 | `reader`는 근거 경로, 사실·추론·미확인, 판정, 누락을 담은 조사 요약 또는 리뷰 판정을 반환합니다. 질문을 모두 다루면 complete, 일부만 다루면 partial, 시작할 수 없으면 blocked입니다. 최종 수용·통합 책임은 owner입니다. |
| 자원·작업 공간 | reader는 공유 체크아웃의 지정 파일만 읽으며 파일 쓰기, Gradle 실행, 기기 변경, 재위임을 하지 않습니다. 읽기 전용 권한 강제가 없다면 제한은 **지침(advisory)** 수준이라고 밝혀주세요. |
| 소유권·동시성 | 쓰기는 owner가 직렬 수행합니다. 선언만으로 독점권이 보장되지 않습니다. 외부 편집 여부를 diff로 재확인하고, 같은 파일의 병렬 수정은 중단·직렬화해주세요. 같은 체크아웃·Gradle 캐시·기기를 공유하는 검증도 직렬화하며, 병렬 검증은 이 자원이 실제로 격리된 경우에만 허용해주세요. |
| 권한·모델 | reader는 파일/git 읽기에 필요한 도구만 사용하며 네트워크·쓰기·spawn 권한은 기본으로 요구하지 않습니다. owner의 쓰기·검증도 요청 범위와 환경 권한 안에서 수행해주세요. 모델 정책은 `inherit`이며, 모델 ID나 전용 런타임 없이 순차 수행 가능해야 합니다. |
| 소통·에스컬레이션 | 결과·질문·충돌·실패는 owner에게 전달하고, owner가 해결하거나 필요한 정보/권한을 사용자에게 요청합니다. 통신 채널이 없으면 owner가 같은 질문을 직접 조사해주세요. 영구 공유가 필요할 때만 아래 기록을 사용해주세요. |

### 실패 처리와 영구 인계

- 작업자 생성 실패, 모델·도구·런타임 기능 부재, 작업 공간 구성 실패에는 보존된 결과를 받아 단일 에이전트·순차 수행으로 전환해주세요. 없는 능력이나 격리를 있는 것처럼 표시하지 마세요.
- 권한 거부는 우회하지 말고 허용된 읽기·문서 작업을 계속해주세요. 리소스 충돌은 해당 작업을 중단하고 직렬화해주세요. 통신 실패·부분 실패·결과 누락은 owner가 가능한 범위만 재조사하고 누락을 명시해주세요. 서로 다른 근거는 원본과 대조하고 해결되지 않은 차이는 남겨주세요.
- 환경/도구 실패는 원인에 근거한 진단 또는 대체 경로를 **한 차례** 시도한 뒤, 같은 실패가 반복되면 멈춰주세요. 코드 실패는 관련 수정이 있을 때만 재검증해주세요. 버전·의존성·SDK를 검증 통과 목적으로 임의 변경하지 마세요.
- `complete`는 요청 범위의 수용 기준을 충족한 상태입니다. 산출물은 있으나 필요한 검증/리뷰가 남으면 `partial`, 필수 입력·권한 등이 없어 의미 있는 진행이 불가능하면 `blocked`입니다. 선택하지 않은 불필요한 검증은 미실행 이유를 적되 완료를 막지 않습니다.

영구 기록이 필요하면 `_workspace/{phase}_{role}_{artifact}.md`를 사용해주세요. `phase`는 `01` 조사, `02` 계획, `03` 수행, `04` 리뷰, `05` 검증, `06` 최종 인계이며 `role`은 `owner` 또는 `reader`입니다. `artifact`는 `{topic}-{run}`으로 정하고, 실행 ID `run`은 한국 시간 기준 `YYYYMMDD-NN`으로 예약해주세요. 예: `_workspace/06_owner_harness-20261016-01.md`입니다. 시작 시 해당 실행 ID의 기록 존재 여부를 확인하고, 새 실행에는 다음 번호를 사용해주세요.

필수 섹션은 **생산자, 소비자, 경로, 기준 상태(commit·기존 diff), 요청 범위, 근거/결정, 검증 결과·미확인, 완료 상태·다음 행동**입니다. owner가 실행 ID와 경로를 지정하며, reader에 쓰기 권한이 없으면 owner가 출처를 표시해 저장해주세요. 완료 기록은 덮어쓰지 말고 후속 실행에서 이전 경로를 참조해주세요. 같은 실행도 수정 이력이 필요하면 artifact에 `-r02`처럼 개정 번호를 붙여 새 파일로 남겨주세요. 단순 진행 상황에는 파일을 만들지 마세요.

## Outputs

조사 요약 → 변경 계획 → 변경 diff/검토 결과 → 리뷰 판정 → 검증 기록 → 최종 인계를 제공합니다. 마지막에는 변경 이유와 파일, 실제 검증과 미실행 항목, 호환성 영향, 범위 밖 발견 사항, 완료 상태를 포함해주세요. 산출물은 요청에 따라 코드·문서 또는 검토 결과이며, PR 생성·게시·릴리스를 자동으로 포함하지 않습니다.

## Validation

제품 변경에는 [위험 기반 검증 지침](references/validation.md)을 사용해주세요. 기본 예제 테스트만 통과한 것을 핵심 회귀 검증 완료로 표현하지 마세요.

하네스 변경에는 frontmatter의 `name`/`description`, 폴더명, 실제 경로·내부 링크, 역할·산출물명, 범위 및 원본 문서 중복 여부를 확인해주세요. 제품 코드 변경 없이 다음 요청을 dry run하여 선택한 절차·기대 산출물·완료 판단을 기록해주세요.

- 정상: “스크롤 종료 후 활성 탭이 잘못 선택됩니다. 수정해주세요.”
- 경계: “README 오탈자 하나만 수정해주세요.”
- 실패: “회귀 검증이 필요한데 기기 또는 작업자 도구가 없습니다.”

dry run은 절차 검증이며 제품 테스트 결과와 구분해주세요. 실제 빌드·테스트 성공 여부는 실행 근거가 있을 때만 기록해주세요.
